## simple-code-indexer
- **Workspace walks must prune ignored dirs (`os.walk` + `dirnames[:]`), never `Path.rglob("*")`** — rglob descends into `.venv` (tens of thousands of files) over the Docker Desktop bind mount, which made the startup reconcile take so long that the phase-2 probe timed out with only 6 files indexed. `indexer.iter_workspace_files` prunes; keep it that way if refactoring.
- **The watcher is now one recursive watch on the workspace root** (2026-11-10). watchdog maps `recursive=True` to a single `ReadDirectoryChangesW(..., bWatchSubtree=TRUE)` and one emitter thread; `schedule()` itself does no tree walk. The old one-watch-per-directory design created one thread and handle per directory (a Visual Studio workspace reached 3,227 threads — ISS-7), so do not reintroduce it. watchdog **does** walk a newly created directory to synthesize sub-events (`generate_sub_created_events`), so creating a huge tree (e.g. `.venv` during `uv sync`) while the server runs can briefly delay event dispatch; the sweep is the backstop. **Every handler drops `IGNORE_DIRS`, the active log file, and `.gitignore` matches silently before any event logging** (`watcher.build_handler.excluded`). Logging first made an active-log-file write log to the active log file and re-trigger itself indefinitely (ISS-9, fixed 2026-11-11); keep all event logging behind `excluded()`.
- **`.gitignore` support is workspace-local and layered** (`ignore.IgnoreRules`, pathspec): root and nested `.gitignore` files are honored, the deeper file wins, and matching is case-insensitive on Windows (git's `core.ignorecase` default). Every **ancestor directory is checked before the path itself**, so a nested `!keep.py` cannot re-include a file under an excluded parent directory (matching git's rule); per-file checks such as `index_one_file` must go through `IgnoreRules`, not only the `IGNORE_DIRS` test. `.git/info/exclude`, `core.excludesfile`, and a parent repo's `.gitignore` above `WORKSPACE_ROOT` are deliberately ignored. `IGNORE_DIRS` is still applied first and remains the fallback. A sweep drops rows for files that become ignored (they disappear from the walk), and a `.gitignore` edit enqueues a sweep; `get_status.ignored_dirs`/`ignored_files` report the last pass.
- MCP SDK is **2.x** (installed `mcp==2.3.0`): the decorator API from the original design document (`@server.list_tools`) no longer exists — handlers are constructor kwargs (`Server(name, on_list_tools=…, on_call_tool=…)`), and models are constructed with **snake_case** field names (`input_schema=`, `is_error=`), serialized camelCase on the wire.
- Ruff 0.17 formats Python code blocks inside `*.md` and wanted to rewrite the design document — `pyproject.toml` excludes `*.md` from ruff.
- **llama.cpp embedding endpoint size limits**: the compose file sets `LLAMA_ARG_UBATCH=2048`; an input larger than the physical batch still returns HTTP 500 (`input (N tokens) is too large to process`). The env names matter: this build reads `LLAMA_ARG_BATCH`/`LLAMA_ARG_UBATCH`, not `..._SIZE`. With the wrong names llama.cpp ignores them and resets n_batch/n_ubatch to 512 (and rejects ~560-token inputs). `embed.embed_texts` still splits oversized texts into ≤1200-char pieces and mean-pools the piece vectors — keep that guard for older containers.
- Loopback connections to closed ports on this Windows host take **2–4 s to fail** (not instant RST) — unit tests must not hit the network; `test_indexer`/`test_watcher` stub `embed.embed_texts`, and `embed.py` caps connect timeout at 1 s.
- **Filename matching must run before the extension check**: `Path("CMakeLists.txt").suffix == ".txt"` and `Path("Dockerfile").suffix == ""` — `path.suffix` alone cannot express those, hence `Settings.allowed_filenames` + `config.is_allowed`. `Path(".vimrc").suffix` is also empty; `.vimrc` is registered as a FILENAME (and `.vimrc` as an extension for `foo.vimrc`). This ordering is what keeps `CMakeLists.txt` working now that `.txt` belongs to the denied `vimdoc` language.
- **tree-sitter-language-pack downloads grammars on demand**: on a fresh machine only `['cpp','python']` are local until `get_parser` fetches the rest. Startup prefetches in a daemon thread (`PREFETCH_GRAMMARS=0` to disable), but only the **symbol-mapped** grammars (`registry.mapped_grammars()`, ~30) — prefetching all ~370 would trigger a download storm for no benefit. Offline first-use falls back to the regex symbol scan. Unit tests that parse non-python/cpp languages must stub `parse._parser`.
- **The pack cannot create its own cache root on Windows**: it derives the download directory from the profile (`%LOCALAPPDATA%`, else `%USERPROFILE%\AppData\Local`), and when that path does not exist it raises `DownloadError: Could not determine a cache directory` instead of creating it — it never falls back to `HOME`/`XDG_CACHE_HOME` on win32. `TREE_SITTER_LANGUAGE_PACK_CACHE_DIR` is the documented override and is the only reliable answer; the pack creates a *missing override directory* happily, so it needs no pre-creation. `tests/conftest.py` therefore always sets it (the developer's existing cache, else a session-scoped `tmp_path_factory` directory). Leaving it as a "pin only if a cache already exists" conditional breaks every parse-dependent test on a clean Windows runner — 52 failures on `windows-latest`, 2026-11-27, fixed by making the override unconditional.
- **The pack's own detector is never used at runtime** (`detect_language_from_path` / `detect_language_from_extension`): it maps `.h` → `c`, `.txt` → `vimdoc`, `CMakeLists.txt` → `vimdoc`, and `Dockerfile`/`Makefile` → `None`. `languages/catalog.py` is the single source of truth; deliberate deviations from the upstream table live in `tools/gen_language_catalog.py` as `EXT_OVERRIDES` (`.h`→`cpp`, `.m`→`objc`, `.tsx`→`tsx`) and `FILENAMES`.
- **Data formats are never indexed, and that is enforced structurally**: `catalog.DATA_FORMATS` (json, yaml, toml, xml, csv, markdown, plaintext/`.txt`→vimdoc, rst, latex, regex, ini, properties, and the VCS/config grammars) are present in the table but **not registered**, so `registry.detect()` returns `None` and `is_allowed` never sees their extensions. `.txt` matters most: it is `vimdoc`, so a registered `.txt` would parse `requirements.txt`/`LICENSE.txt` as Vim documentation. `tests/test_language_catalog.py` guards the leak.
- **A language id is the pack grammar name** — `csharp`, not `c_sharp`; `.tsx` resolves to `tsx`, `.zsh` to `zsh`. Changing an id changes what `files.language` stores, so bump `catalog.VERSION`: `runtime._reconcile_language_catalog` drops rows whose stored language no longer matches detection (or whose path is no longer allowed) and the startup sweep re-indexes them.
- **`symbol_lookup` reports its own blind spots**: a language with no symbol map and no extractor relies on the pack's `process()` with `symbols=True` (both passes merged). When the lookup finds nothing it returns `coverage` (`none`/`partial`/`full`) plus a `hint`, so a missing symbol is distinguishable from a language that cannot resolve symbols. `SYMBOL_FALLBACK=0` disables the `process()` step. `catalog.SYMBOL_GAPS` is the authoritative list of languages with no map; `get_status.languages_without_symbol_maps` reports its size.
- **Symbol maps are derived, never guessed** (ADR-020): the generator reads each grammar's tags query (`get_tags_query`) and validates every node type against that grammar's node-kind table, failing loudly on a rename. Adding a hand-written `SYMBOL_NODES` entry is only for grammars with no usable query — and it is validated the same way. `node_kind_is_supertype()` cannot be used to filter node kinds: this binding reports `True` for punctuation such as `,`.
- **A symbol-map change must bump `SYMBOL_MAP_VERSION`, not `CATALOG_VERSION`**: `catalog.VERSION` changes trigger `runtime._reconcile_language_catalog`, which drops rows and forces a re-embed; `SYMBOL_MAP_VERSION` only enqueues `indexer.backfill_symbols`, which re-parses and rewrites `symbols` alone. A map can improve with no file changing, so without the bump the sha256 and `(mtime, size)` short circuits would never reach an existing index.
- **Injections queries are written for highlighting, not for symbols**: of the 142 catalog grammars that ship one, most target CSS, comments, regexes, HTML, or doc comments, and one region can match several patterns (Svelte captures a `<script>` body as both `@javascript` and `@typescript`). The runtime therefore indexes only `elixir`/`javascript`/`php_only`/`typescript` regions, for the six hosts in `INJECTION_HOSTS`, and deduplicates by span with `_INJECTION_PRECEDENCE`. `pattern_settings()` exposes `#set! injection.language` but **not `#offset!`**, so a query that captures a whole tag and trims it (Heex `<script>`/`<style>`) cannot be followed — do not add a per-host offset table to work around it. `php_only` is not a pack grammar: it is parsed through `php` behind a `<?php ` prefix (`_INJECTION_PREFIXES`), and any prefix must stay newline-free so fragment lines still map onto host lines.
- **`uvx --from <repo> simple-code-indexer` preserves the process cwd** (verified) — that is what makes the cwd workspace source work for CLI launches. The *first* launch after a source change rebuilds and installs into a cached environment (~5 s; ~0.3 s warm), so a slow first `mimo mcp list` is not a hang. The ephemeral env is separate from the repo's `.venv`.
- **Collection names are case-folded path hashes**: on a case-sensitive filesystem `/x/App` and `/x/app` collapse onto one collection (deliberate — it keeps Windows drive-letter case from splitting one project in two). Slug: non-alphanumerics → `-`, capped at 32 chars, empty → `root`.
- **`meta.qdrant_url` + `meta.qdrant_collection` bind an index DB to exactly one endpoint and collection.** Any mismatch — *including rows written before those keys existed* — drops every row so the startup reconcile re-embeds them; points left in the previous collection are orphaned (delete by hand). The retired global `code_index_2560` is still sitting in Qdrant.
- **Machine state from the Docker era**: `.pytest_cache/` in this repo and `%TEMP%\pytest-of-KJ` are unreadable and undeletable for the current user (container root created them over the bind mount). `uv run pytest` fails on every `tmp_path` test until an elevated shell removes them; the workaround is `uv run pytest -p no:cacheprovider --basetemp <writable dir>`.
- **First use of a workspace collection is a three-way race**: the service-probe thread, the index writer, and a semantic search all call `ensure_collection` at once. Unguarded check-then-create answered `409 Conflict` to the losers, and because indexing is fail-soft that silently cost the workspace *all* its vectors. `ensure_collection` is now serialized in-process and re-checks existence when a create fails, so a create it lost to another process is fine. Reproduced 2026-10-18 while verifying two-workspace isolation; the integration test only passed once this was fixed.
- **`mode: sidecar` is the default (ADR-014)**: each harness's MCP server is a read-only **reader**; one detached daemon per workspace owns `index.db`, `vectors.faiss`/Qdrant, the watcher, writer thread, sweep timer, and managed services. The daemon exits after the last registered session plus `idle_grace_s` (60 s) and is respawned by the next session. `SIMPLE_CI_MODE=embedded` (or `mode: embedded`) restores the old all-in-one process. If a legacy embedded writer holds the lease, the daemon exits and readers serve read-only until it is gone.
- **Writer lease and finalize order (`runtime.WriterRuntime`)**: `start()` acquires `.simple-ci/index.db.lock`; `stop()` stops the watcher, joins the writer/sweep/heartbeat threads, flushes vectors and clears dirty flags while the lease is still held, then releases it last. `db.clear_vector_dirty` is unscoped, so releasing first would let the old process clear the new writer's dirty flags and silently lose vectors. `stop()` is idempotent. The daemon also clears its discovery files while the lease is still held, so a new daemon cannot publish a ready/token file that the old process then deletes. A leftover lock file on disk is harmless (`msvcrt.locking`/`fcntl.flock` die with the process).
- **Sidecar discovery and IPC**: `daemon.json` and `daemon.token` live under `<workspace>/.simple-ci/run/`; the control endpoint is a Windows named pipe `\\.\pipe\simple-code-indexer-<hash>` or a POSIX AF_UNIX socket in a per-user runtime directory. `multiprocessing.connection` authenticates with the token as `authkey`; message bodies are JSON strings, never pickles. Readers validate the ready-file pid and remove a stale file; a spawn lock (`daemon.spawn.lock`) serializes first spawns and the reader backs off between retries.
- **Reader rules**: readers never call `ensure_schema`, `flush`, `reset`, `reconcile`, `upsert_chunks`, or any delete path. SQLite reads go through `db.try_connect_readonly` (missing DB → `ready: false`); FAISS reads through `faiss_store.search_readonly` (reload on mtime/size, missing file → not ready, never creates); Qdrant reads through `validate_collection`/`search_readonly` (never creates). `search_code`, `symbol_lookup`, and `get_status` fail soft while the index is being created.
- **Daemon logging and status**: the daemon writes `<workspace>/.simple-ci/log/writer.log`; each reader writes `reader.log`; `embed.log` belongs to `mode: embedded`. All three use the same `log.max_bytes`/`log.backups` rotation; `reader.log` is shared by every reader, so its rotation is best-effort (a rollover can be missed, never a crash). The old `sci.log*` files are retired: nothing reads or rotates them anymore, so delete them by hand if desired. In a reader, `get_status` merges the daemon RPC (`sessions`, `harnesses`, `writer_*`, `watcher_alive`, `last_sweep`, services) and falls back to `meta.writer_pid` / `meta.writer_heartbeat` when the daemon is unreachable.
- **Daemon crash recovery**: readers keep serving read-only, the supervisor respawns the daemon, and dirty FAISS flags survive; the next startup `reconcile` re-embeds. A force-killed daemon leaves a stale ready file, which the next reader removes after a pid-liveness check. The daemon's `stop` protocol message is authenticated and is mainly for tests/admin.
- **Discovery files are invalidated, not always deleted** (`paths._clear`): Windows denies `unlink` while any handle holds the file open without `FILE_SHARE_DELETE`, and readers poll `daemon.json` every 100 ms, so a shutdown-side delete fails often enough to be routine. `_clear` falls back to truncating to empty, which succeeds under a live read handle; `read_ready`/`read_spawn_claim` already reject empty content and `read_token` returns `None`, so an empty file *is* the absence signal. Never assume a cleared discovery file is gone from disk (a "does the file exist" check is not a liveness check), and never restore a bare `unlink` there.
- **`Listener.close()` does not wake a blocked `accept()`** (Windows named pipe: the pending handle stays open; POSIX: a socket close is not a reliable wake). The daemon therefore sends one authenticated self-connection before closing, and `_accept_loop` recognises it by the stop event and exits; without it every shutdown burns the full 2 s `join` timeout. That connect runs on a bounded thread (`_WAKE_TIMEOUT_S`) because `multiprocessing.connection.Client` waits for a pipe instance with **no** timeout — called inline it would hang shutdown forever whenever the accept loop had already died. Do not "simplify" this back to close-then-join, or to an unbounded inline `Client(...)`.
- **Tests that spawn a real daemon** (`tests/test_sidecar_daemon.py`, `tests/test_sidecar_mcp.py`) must stop it in `finally` using the pid in `.simple-ci/run/daemon.json` (`taskkill /PID <pid> /T /F` on Windows), then remove the ready/token files; otherwise a detached daemon can outlive the suite.
- **Every sweep re-embeds chunks whose `embedding_state.status != 'ok'`** (or that have no row), independent of the file hash/mtime short circuits. It stops at the first failing file, so a downed embed endpoint costs one retry per sweep rather than one per pending file; successful chunks are never re-embedded.
- **Several open workspaces share one embedding endpoint** (one writer daemon per workspace, ADR-014; reader sessions only embed queries). `embed.py` splits each request into ≤16-input batches, keeps at most two posts in flight per process, and retries with full-jitter exponential backoff — request-level back-pressure, not an endpoint-wide limiter. N workspaces still multiply the load; `get_status.pending_embeddings` and semantic `search_code.ready` show when vectors are still catching up.
- **The MCP probes drain the server's stderr on a thread** (`tests/mcp_probe._spawn`, shared with `tests/live_watch_probe.py`). The server logs INFO per indexed file and per tool call; an unread `stderr=subprocess.PIPE` fills and blocks it inside a log write. `PROBE_TIMEOUT` (default 180 s) bounds the run. Do not reintroduce a bare `stderr=subprocess.PIPE` there.
- **`ensure_collection` validates the existing collection's vector size against `EMBED_DIM`** (and rejects named-vector collections): a mismatch raises `QdrantUnavailable` with both sizes — indexing stays fail-soft (`qdrant_ok: false` in `get_status`) but no longer silently accepts a vectorless workspace.
- **A semantic query is nearest-chunk, not a lexical match**: asking a workspace for a symbol it does not contain still returns its own closest chunk. Isolation tests must assert "every hit comes from this workspace", never "an unrelated query returns nothing".
- **`uv run` re-syncs after every source edit**, and `uv run simple-code-indexer setup` builds the project first, so an extra build/sync line is normal rather than a hang.
- **Config discovery leaks into tests unless disabled**: the autouse fixture in `tests/conftest.py` sets `SIMPLE_CI_CONFIG=none`. `test_multi_workspace_isolation` spawns a child process, so it also sets the variable explicitly (a monkeypatch is not inherited).
- **Harness path expansion takes an explicit home**: `HarnessSpec.candidates(..., home=...)` exists so the wizard can write to the fake home in tests (and respects `Path.home()` in production). Do not regress to bare `expanduser()`.
- **Command Code detection must not use the `cmd` binary** — on Windows that is the shell, so every machine would look like it has Command Code installed. Its plugin only checks `~/.commandcode`.
- **Checkout detection claims the tree the module runs from, not any tree that exists**: `harnesses._repo_harnesses_dir` and `setup_wizard._default_repo_root` both require an ancestor whose `src/simple_code_indexer/` contains the running `__file__`. Testing only that the tree exists adopted the enclosing project of an installed package — and, because `--basetemp` values under the repo put `tmp_path` inside this checkout, a fake `<site-packages>/simple_code_indexer/__init__.py` walked up into the real repo and broke the negative test. When writing such a test, patch `__file__` and keep the fake tree outside the repo, or assert both helpers.
- **JSONC comments are lost on rewrite**: `harnesses/_json.py` strips `//` and `/* */` to parse OpenCode files, then writes strict JSON. `write.install` backs the file up and refuses to write a document it cannot parse; keep both behaviors.
- **Codex config is merged with marker comments** (`# >>> simple-code-indexer >>>`), not a TOML round-trip: `tomllib` cannot write, and rewriting would destroy user comments/order.
- **Managed services block the startup path** (by design) for up to `startup_timeout_s`; they are fail-soft afterwards (`get_status.services`). Harness configs from the wizard use `timeout: 120000` because of this.
- **sqlite-vec is the default vector store** (`vector_store: sqlite-vec|faiss|qdrant`, `VECTOR_STORE` wins). Its vectors live in a `vec_chunks` virtual table inside `index.db`, `rowid` = `vector_labels.label`; upsert/delete and the label rows commit in one transaction. `vector_store.py` no longer branches: it validates the name and dispatches through `_STORES` to a backend module implementing `STORE_CONTRACT` (a contract test iterates the registry).
- **`vec_chunks` is created by `sqlite_vec_store`, never by `db.ensure_schema`**: creating a virtual table requires the extension loaded on that connection, and readers must never create it (`search_readonly` reports "semantic index is not ready" instead).
- **Every sqlite-vec connection loads the extension itself.** `db.connect`/`try_connect_readonly` stay backend-agnostic; `sqlite_vec_store._connect` adds `enable_load_extension` + `sqlite_vec.load` + `PRAGMA mmap_size`/`cache_size`. A Python built without loadable-extension support raises `VectorStoreUnavailable` (the wizard's `sqlite_vec_store.available()` probe catches this before it becomes a default).
- **`INSERT OR REPLACE` does not work on vec0 0.1.9** (it raises a UNIQUE constraint error). Upsert does `UPDATE ... WHERE rowid = ?` and inserts only when `rowcount == 0`.
- **sqlite-vec fixes the dimension and `chunk_size` in the DDL.** A mismatch drops/recreates `vec_chunks` and calls `db.invalidate_embeddings` so the next sweep re-embeds; it does not delete `files`, so there is no re-parse. Changing `sqlite_vec.mmap_size`/`cache_size` is free (per-connection PRAGMAs).
- **Switching backends re-indexes; vectors are never migrated.** An sqlite-vec identity is `("sqlite-vec", "<dim>:<fingerprint>")` — deliberately path-free, because the vectors are inside `index.db` and renaming a workspace must not re-embed. `vector_store.reset` drops a leftover `vec_chunks` table when another backend becomes the active one.
- **FAISS label ids must never be recycled.** `vector_labels` rows are deleted (file removed, identity invalidated), so `MAX(label)+1` alone would eventually reuse an id; `meta.vector_label_seq` is the monotonic source. A reused id could attach an old vector left in `vectors.faiss` by a crash to a new chunk.
- **The `vector_labels.dirty` flag is FAISS-only bookkeeping.** sqlite-vec commits vectors with their labels and never sets or clears it; keep the column and helpers while FAISS remains selectable.
- **One lock covers the FAISS index *and* the `vector_labels` mapping** (`faiss_store._lock`). Upsert allocates + marks labels dirty, then removes-adds under that lock; `flush` writes the file and clears the dirty flags under the same lock. Splitting either side reintroduces the "flag cleared for a vector not in the file" race.
- **An invalidated identity resets FAISS by writing an empty index immediately** (`faiss_store.reset`), not just in memory: `server._run` calls `ensure_ready` right after, which would happily reload the stale file — and the label sequence was not reset, so colliding ids are possible if the old file survives. A failed reset unlinks the file as a fallback.
- **`embedding_state.qdrant_point_id` is migrated to `vector_id`** in `db.ensure_schema` via a guarded `ALTER TABLE ... RENAME COLUMN`; the `NOT NULL` and no-rebuild behaviour are deliberate.
- **FAISS write paths call `db.ensure_schema` themselves** (`upsert`, `delete_by_path`, `reconcile`, `flush`). The store is usable before the server's startup `ensure_schema`; search is read-only and assumes the table exists.
- **`faiss_store` imports numpy at module load and faiss lazily**; `vector_store.py` lazy-imports `faiss_store` so the Qdrant-only path never pays for either. `faiss.loader` logs its AVX2 probe to stderr on first use.
- **The status payload is a breaking change**: `qdrant_ok`/`collection` are gone, replaced by `vector_store`, `vector_store_ok`, `vector_index` (the FAISS path or the Qdrant collection). `tests/mcp_probe.py` and `tests/test_multi_workspace_isolation.py` were updated to match.
- **`tests/test_multi_workspace_isolation.py` now needs only the embedding endpoint** (it forces `VECTOR_STORE=faiss`), not Qdrant. `tests/service_probe.py` treats Qdrant as optional unless `VECTOR_STORE=qdrant`.
- **`test_indexer`'s fixture sets `vector_store="qdrant"`** because those tests patch `qdrant_store.upsert_chunks`. The patched function must return a list of ids (the router now propagates them into `embedding_state.vector_id`); returning `None` raises inside `zip`.

Other strategies all failed to surface the pruning chunk: 40/120-line windows, 60-line overlap, symbol-boundary chunks, path/symbol headers, and dropping the document prefix (symbol-aware chunks made it worse, rank 27). The model's useful retrieval unit is ~500-1000 chars of code; keep chunks focused. The throwaway harness and per-variant results live in `artifacts/chunk-exp/` (gitignored).
- **Overlapping chunks are deduped at query time** (`server._semantic_hits`): 30x15 windows overlap 50%, so it fetches `limit * 3` vector hits and drops a hit whose line span overlaps a higher-ranked hit from the same file. Without that, a semantic top-10 collapses to ~4.8 distinct files; with it, ~6.1 (the non-overlapping baseline was ~7.1). Do not remove the dedupe while the chunker overlaps.

- **A uv entrypoint shim can outlive its environment**: deleting `<uv tool dir>/simple-code-indexer` by hand (or a failed uninstall) leaves `simple-code-indexer.exe` in `uv tool dir --bin`, and `uv tool list` then reports "No tools installed" while `uv tool install` still refuses to overwrite the shim without `--force`. `install.entrypoint_present()` makes `ensure_tool` treat that state as an existing install, so a plain `install` recovers; a raw `uv tool install` in the same state needs `--force`.
- **A run cannot reinstall the tool environment it is executing from (fixed 2026-11-26)**: `uvx simple-code-indexer setup` reuses an installed tool (`uvx` is not isolated by default), so the setup runs from `<env>\Scripts\simple-code-indexer.exe` → `python.exe`. uv rewrites that console script on every install, and Windows will not overwrite the executable image of the running process: `error: failed to remove file ...\Scripts\simple-code-indexer.exe: ... being used by another process (os error 32)`. `uv tool install --force` is worse — it deletes the environment directory first and dies on `...\Scripts: Access is denied (os error 5)`. `ensure_tool` therefore asks `install.running_from_env()` first: when the receipt already holds the requested editable link (or the pinned version) it returns immediately, and otherwise it raises with the `uv tool install …` line to run from outside. Verified with both `uvx simple-code-indexer install` and `uv run simple-code-indexer install`.
- **Never pass `--force` to `uv tool install` for a live environment**: `--force` deletes the environment directory before rebuilding, and `<env>\Scripts\python.exe` cannot be deleted while any process runs from it — a harness's live MCP reader (`pythonw.exe`) is enough. A plain `uv tool install` replaces packages in place, leaves the interpreter and sibling executables alone (verified: only `simple-code-indexer.exe` is rewritten), and still flips editable↔wheel, so `ensure_tool` passes `--force` only for the orphan-shim case above. `uv tool uninstall` has the same limitation: when the uninstall is itself executing from that environment, `Uninstaller._tool_env_is_self` detects it on Windows, removes everything else, and prints `uv tool uninstall simple-code-indexer` to run after the process exits instead of letting uv fail with `Access is denied` (ISS-001, fixed 2026-11-26). POSIX unlinks the running executable and removes it in-process.
- **A test run can repoint the real harness entries (ISS-023, fixed 2026-11-26)**: `--install-only` ends in `_repin_recorded_harnesses`, which used to read `configfile.global_config_path()` — i.e. `Path.home()` — so `SIMPLE_CI_CONFIG=none` did not isolate it. - **Windows console windows (2026-11-12)**: a console-subsystem child started from a **no-console** parent (GUI harness, `pythonw`, detached process) allocates a new **visible** console window even when stdin/stdout/stderr are redirected to pipes — redirection does not suppress it. `CREATE_NO_WINDOW` gives the child a hidden console; `DETACHED_PROCESS` gives none. Three consequences, all fixed:
  1. `setup_wizard/install.py` now points Windows harness entries at the venv's GUI-subsystem `pythonw.exe` instead of `uv run … python …`; otherwise `uv.exe` itself allocates the window when the harness is an Electron/GUI app. The server speaks MCP normally over the inherited pipes (verified with `initialize` + `tools/list` under `pythonw`).
  2. The sidecar daemon must use `CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP`, **never** `DETACHED_PROCESS`: the venv `Scripts\python.exe` is a redirector that `CreateProcess`es the real interpreter without creation flags, so a detached redirector leaves its child to allocate a visible window for the daemon's lifetime (verified: the redirector had no console, its child had a visible one; with `CREATE_NO_WINDOW` the whole tree's `GetConsoleWindow()` is 0).
  3. `services.py` (`docker …`) passes `CREATE_NO_WINDOW` too, so its console children cannot flash a window from a windowless writer/reader.
- **A VS Code window costs three pythonw processes, not four (ISS-016, fixed 2026-11-19)**: a reader is two OS processes because `<install>/.venv/Scripts/pythonw.exe` (263 KB) is a redirector that re-executes `c:\python312\pythonw.exe` and waits for it; the per-workspace daemon used to add a second pair the same way. `sidecar.client._daemon_command` now starts the daemon as `sys._base_executable` with the reader's resolved `sys.path` (the installed package comes from a `.pth`), so the daemon is one process. - **Reader spawn storm (2026-11-12)**: `_spawn_if_needed` used only a 2→30 s cooldown, so a daemon that took >2 s to publish `daemon.json` (Docker/vector startup) made the reader spawn 2-4 extra daemons; each lost the writer lease and exited, so the user saw several console windows flash and close, leaving one. The reader now refuses to spawn while the Popen child it started is still alive (`_children` pruned by `poll()`), so a slow-starting daemon is waited for instead of raced. Cross-process races remain possible because `_children` is per reader; the spawn lock holder therefore also writes `run/daemon.spawn.json` (child pid + wall-clock timestamp) before releasing the lock, and peers skip spawning while that pid is alive and the claim is under 10 minutes old. Without the claim, a duplicate spawned just before the winner was force-killed could later win the freed lease and outlive the test that stopped the published daemon.

- **The `SIMPLE_CI_HARNESS` marker is optional at runtime**: the code updates via `run_server.py`'s
  `git pull`, but `~/.commandcode/mcp.json` keeps its old entry until
  `simple-code-indexer setup --harnesses commandcode` rewrites it. An entry without the marker is not left
  indexing the editor's install directory: when the cwd is implausible (the user home or a live
  ancestor's executable directory, `config._implausible_reason`), `discover_workspace` is retried
  with `require_marker=False` and asks every plugin that declares a resolver. A *plausible* cwd is
  never overridden, so a terminal-launched server still indexes where it was started. If nothing
  publishes a workspace there, `load_settings` raises a `ConfigError` naming the directory instead
  of silently building an empty index (Program Files is not even writable for the log file).
  The marker remains the fast path — it names the one plugin to ask — so still re-run setup when
  convenient. The install-directory check needs the executable path: Windows and Linux expose it
  (`QueryFullProcessImageNameW`, `/proc/<pid>/exe`), macOS has no portable equivalent, so there
  only the home-directory part applies and a macOS editor install relies on the marker.
- **Command Code discovery files are not self-cleaning**: `~/.commandcode/ide/<ide>-<8hex>.json`
  accumulates dead windows. `harnesses/commandcode.py` therefore matches `pid` against the live
  ancestor chain (`parent_watch.ancestor_chain`, which ignores the spawn-shell boundary) plus the
  ancestor's image name, never by file recency or `timestamp`. The `cmd.exe` that the extension's
  `shell: true` inserts between the extension host and our interpreter is therefore transparent to
  both discovery and `parent_watch`.
- **OpenCode keeps MCP servers alive while its background service runs**: `opencode-cli serve --service` outlived the desktop UI, so the server's stdin never closed and it kept sweeping (two sessions → two servers; one was indexing `VideoDeduper` with a 300 MB index). Closing the UI does not stop the server by design (the watchdog watches the service, see the next bullet); stop the service (`opencode service stop`) or kill the process tree. A venv-python launch also appears as **two** processes (uv's 274 KB trampoline spawns the base interpreter), and the `uv run` entry adds the uv launcher on top, so count servers by their `index.db` lock, not by `python.exe`.
- **The watchdog watches the harness process only** (ISS-10, fixed 2026-11-11): `parent_watch.harness_process` walks past `uv`/`uvx` and the venv `python.exe` trampoline — recognized by the `\Scripts\python` image path on Windows, or by a `uv` parent on POSIX — then watches exactly the first remaining process and nothing above it. A shell is crossed only while everything below it is our own launch plumbing (ISS-015: the VS Code extension's `shell: true` puts `cmd.exe` between the extension host and our interpreter); a shell above the harness still ends the walk, so a terminal-launched server has no harness. For OpenCode the watched process is `opencode-cli serve --service`, so the server lives as long as that service does: closing the desktop UI no longer stops it, and a service *reused* by a later UI (the 427588 / 489696 case) is covered rather than missed. `opencode service stop` kills its MCP children (no `shutting down`/`workspace lock released` lines), while a clean stdin close still shuts the server down normally. Caveat: a python-based harness launched *through* `uv` cannot be distinguished from the venv trampoline and would be skipped; all shipped entries use native hosts, so this is theoretical. `opencode mcp list` printed "No MCP servers configured" immediately after `service start`; re-running it (e.g. with `--print-logs --log-level debug`) read the config and reported `✓ simple-code-indexer connected` — treat the first result as a service warm-up race, not a missing entry. A `setup.py` re-run rewrites the OpenCode entry from scratch, which also removes hand-added `environment` keys.
- **Three simultaneous harnesses (2026-11-13, Pi + Goose + OpenCode)**: one sidecar daemon served all three readers; `writer.log` is the authoritative session timeline (`sidecar client connected` / `session registered … sessions=1/2/3` / `disconnected` / `no sidecar sessions for 60 s`). `get_status.sessions` is a **point-in-time** snapshot: Pi reported 2 because it read before Goose connected, and its `node.exe(<pid>)` entry was its own harness, not Goose (`goose.exe`). Every agent should re-read `get_status` immediately before writing results and record the **maximum** sessions seen. A `pythonw.exe` reader does not appear in `python.exe`-only process filters; include `pythonw.exe` (venv trampoline + base interpreter). Reader `unregistered`/`closed` lines appear only on a clean stdin close; harnesses that kill the child (`opencode service stop`, app exit) leave none, so judge shutdown from `writer.log`. OpenCode's UI close leaves `opencode-cli serve --service` alive; run `opencode service stop` to end the session. The run also confirmed workspace-free entries and cwd-only inference: all three `get_status.workspace` values matched the repo with no `cwd`/`WORKSPACE_ROOT` in any entry.
- **The periodic reconciliation sweep is off by default** (`sweep_seconds: 0`; `SWEEP_SECONDS` overrides). The watcher handles live saves and the unconditional startup reconcile still builds the first index and drops stale rows. `setup.py` asks whether to enable it (default No) and `--sweep-seconds N` answers non-interactively; existing configs written by older wizard runs contain `45` and keep it until reconfigured. When enabled, the interval doubles whenever the watcher saw no events *or* the last sweep found no changes, up to `SWEEP_BACKOFF_MAX_S` (600 s), and resets when both saw activity. With sweeps disabled the `sweep-timer` thread stays dormant, polls `pending_embeddings` every `DORMANT_POLL_S` (60 s), and temporarily re-enables sweeps while chunks need vectors; it backs off the same way while the count does not change and stops again at zero, which is what heals a transient embedding outage without a full walk every minute. A deletion the watcher misses while the server is running therefore stays in the index until the next start (the startup reconcile still drops stale rows), and a full work queue falls back to that same startup pass. `get_status.sweep_seconds` reports the mode (0 = off).
- **The existing Qwen3-4B container was created with `LLAMA_ARG_POOLING=mean`**; after recreating it with `last` on 2026-11-07, retrieval jumped (R@1 0.100→0.525, nDCG@10 0.317→0.719). Qwen3-Embedding is trained for last-token pooling. The wizard warns when it detects a Qwen3 model in a mean-pooling container (worse retrieval, not a crash); keep the warning.
- **`faiss_index_path(settings)` is a function in `config.py`, not a `Settings` attribute**; the benchmark originally called `settings.faiss_index_path` and crashed. Use the function.
- **Benchmark state**: `tests/retrieval_bench.py` must run in a fresh process per model/backend (FAISS and embed module globals leak otherwise). It writes a temp `SIMPLE_CI_CONFIG` and sets `WORKSPACE_ROOT`; `--local-path DIR` sets `INDEX_DB`/`FAISS_PATH` into `DIR` **after** the env overrides are cleared and re-derives the Qdrant collection from `DIR` too, so a run never touches a live workspace index or collection — `tests/bench_matrix.py` passes a per-run scratch folder under `artifacts/bench/<timestamp>/local/`, so every run gets its own collection. `QDRANT_COLLECTION` is still cleared with the other env overrides and cannot pin a collection; isolation comes from `--local-path`. `--reset` deletes `index.db*`, `vectors.faiss` (FAISS) or the derived Qdrant collection, and warns when it is about to hit `<workspace>/.simple-ci/index.db` because no `--local-path` was given. Existing embed containers both map host `8080`, so `tests/bench_matrix.py` stops the other one before starting the target. Reports land in `artifacts/`, which is `.gitignore`d and therefore no longer indexed.
- **Long benchmark runs need a background shell**: this harness caps a single `shell_command` at 10 minutes. Use `run_in_background=true` + `shell_output`/`shell_tasks` for the Nomic download and multi-model matrices.
- **Redirected home for live setup tests**: set `USERPROFILE`, `HOME`, `APPDATA`, and `LOCALAPPDATA` for the child process. `Path.home()` follows `USERPROFILE` on Windows. **A non-dry-run `setup` or `uninstall` is machine-wide**: it writes/removes the global config, the uv tool environment, harness configs and `~/.simple-ci/`, so never exercise one against a real profile — redirect `HOME`/`USERPROFILE`/`APPDATA`/`LOCALAPPDATA` first. There is no scoping flag for this any more.
- **Uninstall is record-driven**: `setup.harnesses` (`{name, config}`) in the global config is the only source. Unrecorded harnesses are deliberately not scanned, so deleting `config.yaml` by hand leaves their entries behind. Removal is idempotent and also deletes the `<config>.bak.<YYYYmmdd-HHMMSS>` backups `write.install` created, then prunes emptied parent dirs up to home (`install.prune_empty_dirs`). It removes the uv tool environment with `uv tool uninstall` — except on Windows when the running command is that environment, where it defers and prints the command for after the process exits (ISS-001); it never touches a source checkout or any directory it did not create.
- **Removing a harness entry re-serializes JSON**: the same caveat as install — OpenCode `.jsonc` comments are lost on rewrite. Codex TOML removal only strips the `# >>> simple-code-indexer >>>` marker block, so the rest of the file (comments included) is untouched.
- **Uninstall compose cleanup only touches our compose file**: `docker compose -f ~/.simple-ci/docker/docker-compose.yml down --remove-orphans`, fail-soft when Docker is down. Externally managed containers and `--embedding-url` endpoints stay; workspace `<project>/.simple-ci/` indexes are never deleted.
- **A failed harness edit keeps `config.yaml`**: the record is needed to retry, so uninstall does not delete the config when any `write.remove` failed (exit code 1) — fix the malformed harness config and re-run. A compose failure is fail-soft and still deletes the config. On Windows a uv tool environment whose interpreter is in use by a running harness cannot be fully removed; close the harness and re-run.
- **Uninstall reaches machine-wide state, so tests MUST redirect the profile**: `tests/test_uninstall.py` has an autouse fixture setting `APPDATA`/`XDG_DATA_HOME`. A run without isolation deletes the developer's real global config, `~/.simple-ci/` assets, and recorded harness entries.
- **Runtime logging is stderr INFO + `<workspace>/.simple-ci/log/embed.log` DEBUG** for `mode: embedded`; the sidecar daemon uses `writer.log` and readers use `reader.log` (same rotation settings). The file handler sits on the **root** logger with a filter (`simple_code_indexer.*` at the configured level, every other logger at WARNING+) so `mcp` dispatch failures land in the file without `httpx`/`mcp` INFO spam. `configure_console()` gives the stderr handler its **own** INFO level — a plain `basicConfig(level=INFO)` leaves it at NOTSET, and propagated DEBUG records from the package logger would then print to stderr.
- **The log path follows `index_db_path.parent`**, so `INDEX_DB=/elsewhere/x.db` moves the logs too; `Settings.log_level` (default `debug`) is file-only, stderr never goes below INFO. `logging_setup.configure_file` is fail-soft (unwritable dir → stderr warning, `get_status.log_file: null`), and `detach_file()` exists so tests never leave an open handle that breaks Windows `tmp_path` cleanup.
- **The package logger is pinned to DEBUG** by `configure_console()`; DEBUG records are then filtered by each handler (file: `log.level`, stderr: INFO). Do not raise the root logger instead — that would also let third-party DEBUG through and the file filter alone decides what is written.
- **`threading.excepthook` + `sys.excepthook` are chained, not replaced**: a dead daemon thread (`sweep-timer`, `watcher`, `index-writer`) is logged at CRITICAL with its traceback, and the previous hook still prints to stderr. `install_excepthooks()` is idempotent; tests that call the global hook must stub the previous one or pytest emits `PytestUnhandledThreadExceptionWarning`.
- **A freshly written global entry is picked up by the always-on OpenCode service (2026-11-26)**:
  `opencode-cli serve --service` loads `~/.config/opencode/opencode.json` as soon as the wizard
  writes it and starts its own reader for whatever workspace it is pointed at — after
  `setup --harnesses opencode,commandcode` the writer logged `sidecar client connected …
  harness=opencode-cli.exe(29180)` with no ACP session running. That reader makes
  `get_status.sessions` read 2 and fails the ACP probe's `one registered session` check. Run
  `opencode service stop` (then `service status` → `stopped`) before an ACP run; ACP spawns a
  private per-process server, so it is unaffected. This is the same root cause as the "keeps MCP
  servers alive while its background service runs" bullet above, reached from the setup side.
- **ACP mode is the automatable harness path** (`tests/acp_probe.py`, 2026-11-18): `opencode acp` runs a private per-process server and exits on stdin close, so a script can spawn it, `session/new`, and read tool payloads without a human or a GUI. It never touches `opencode-cli serve --service`, so the "reused service keeps MCP children alive" quirk from the GUI runs does not apply. Inject the server on `session/new` with its **canonical** name (`simple-code-indexer`): a different name adds a second reader and `get_status.sessions` reports 2. On 2.2.5 the configured entry is the only server the harness starts and the injected one is never reached, so never mask it: `tests/acp_probe.py` fails the run before spawning the agent when that entry does not launch the tool environment (`references/acp-test-process.md` §6.2).
- **An ACP harness kills its MCP reader on exit** (2026-11-19): the reader gets no chance to log `unregistered`/`closed`, and the daemon logs `sidecar client disconnected ... registered=True (sessions=0)` plus a DEBUG traceback. That is a clean shutdown; judge it from `writer.log` (`no sidecar sessions for 60 s`, `vector store flushed`, `workspace lock released`, `sidecar stopped`), not from reader-side lines.
- **Always drain an ACP agent's stderr on a thread**: OpenCode and `cmd acp` both log to stderr, and an unread pipe blocks the agent (and the MCP server under it) inside a log write. This was a real 5-minute "hang" while writing `tests/acp_probe.py`; it is the same failure mode already documented for `mcp_probe`.
- **An ACP client must separate requests from notifications**: a message with **both** `id` and `method` is a server-initiated request (`session/request_permission`) and must be answered; a message with `method` and **no** `id` is a notification (`session/update`) and must be dispatched. Handling `method` first kills the reader thread, and every later `session/prompt` then times out — which looks exactly like a wedged harness.
- **A permission request left unanswered hangs the tool call**: `session/request_permission` blocks the agent until the client replies. Automation answers `allow_once`; both harnesses ran this repo's server that way (Command Code prompted once per tool call, OpenCode did not prompt at all).
- **ACP tool results are structured, but model adherence is not**: parse the JSON on `tool_call_update`/`content[].content.text` (search for the first `{` and use `raw_decode`; models wrap it in fences and prose) and never assert on the model's summary. Free `opencode/*-free` models answered prompts with no provider login yet skipped tool calls intermittently, so a probe must retry once and poll readiness rather than sample a single response.
- **`opencode acp` rejects `--auto`** (2.2.5): the child exits during `initialize`. Permission behaviour is client-side over ACP, not a CLI flag. The OpenCode desktop bundle's binary is at `%LOCALAPPDATA%\Programs\ai.opencode.desktop\resources\opencode-cli.exe` and is not on `PATH`; because `cmdc.cmd` usually is, anything that resolves the agent by bare name can silently test Command Code instead of OpenCode.
- **Command Code is an ACP server, not a client** (`cmd acp`, verified 1.89.1: `initialize` → `agentInfo`, `session/new`, `session/prompt` → reply). It can be driven by an ACP client but cannot itself drive `opencode acp`, so an automated harness must speak the protocol directly (`references/acp-test-process.md`).
- **A POSIX zombie still answers `kill(pid, 0)`** (2026-11-21): a harness killed while its parent has not reaped it stays in `/proc` with state `Z`, so the watchdog's liveness check must read `/proc/<pid>/stat` (start time in field 22, state in field 3) and treat `Z`/`X` as gone — PID reuse alone is not enough. macOS has no `/proc`, so only the signal-0 fallback applies there.
- **Process-name tables are platform-specific** (2026-11-21): `parent_watch._SHELL_NAMES`/`_BOUNDARY_NAMES` are built for the host, so unit tests feeding `cmd.exe`/`explorer.exe` pass vacuously on Linux (and the reverse). `tests/test_parent_watch.py` picks names from `sys.platform`; keep it that way.
- **Dev scripts carry no shebang** (2026-11-21): `core.filemode` is `false` on the Windows dev host, so git tracks every file as `100644` and a `#!` line passes local `ruff check` but fails the Ubuntu CI job with `EXE001` (`tools/release.py` did). Invoke scripts as `python tools/<name>.py`; if a shebang is ever required, pair it with `git update-index --chmod=+x <path>` in the same commit.
- **Detection probe timings measured on the dev host** (2026-11-27): `zed --version` 7 ms, `code --version` 103 ms, `cursor --version` 126 ms, `windsurf --version` 175 ms, `pi --version` 298 ms, `mimo --version` 1.4 s, `command-code --version` 2.1 s, `openclaw --version` 4.2 s. The npm-installed CLIs pay for a `.cmd` shim plus Node startup, which is why `_probe.PROBE_TIMEOUT_S` is 10 s rather than 5 — a tighter cap turns a working CLI back into `binary`/`dir` detection silently. The same commands through PowerShell took 17 s (`command-code`), so measure with the Python runner, not the shell.
- **A GUI binary must never be a detection binary** (2026-11-27): the probe *executes* the binary with `--version`, so any client whose executable would open a window instead of printing and exiting declares `BINARIES = []` and relies on `HOME_DIRS`. Claude Desktop has no CLI at all; Zed is worse, because a runnable `zed.exe` here is the editor but the same name on a machine with authzed's SpiceDB CLI is a different program.
- **`opencode-cli` is not on `PATH`**: the OpenCode desktop bundle ships it at `%LOCALAPPDATA%\Programs\ai.opencode.desktop\resources\opencode-cli.exe`, so it can be a `CLI_BINARIES` fallback for `cli_add` but must not be a `BINARIES` probe target.
- **`hermes mcp add` cannot be scripted yet**: it always ends with an interactive "Enable all N tools? [Y/n]" prompt and has no `--yes` (tracked upstream). The Hermes plugin therefore declares no `cli_add` and the wizard merges `~/.hermes/config.yaml` directly; add a `cli_add` only once a non-interactive flag exists.
- **`openclaw mcp` needs a current build**: OpenClaw's own docs (`docs.openclaw.ai/cli/mcp`) define the client-side registry as `openclaw mcp set|unset|list|status`, writing `mcp.servers` in `~/.openclaw/openclaw.json`. An older build (2026.2.26, `bc50708`) predates MCP entirely — it has no `mcp` command *and* its config schema rejects `mcp`/`mcpServers`/`servers`, so `openclaw config set mcp.servers.<name> …` writes the file and then exits 1 with "Unrecognized key". A `unknown command 'mcp'` failure therefore means "upgrade OpenClaw", not "the plugin is wrong"; do not substitute `openclaw config set`.
- **The two meanings of `--harnesses`** (2026-11-27): bare `setup --harnesses` prints the detection table and exits, while `setup --harnesses all|cursor,pi` selects. It is one argparse argument with `nargs="?"` and a `LIST_HARNESSES` sentinel, so combining the bare form with `--uninstall`/`--install-only` is a parser error rather than a silently ignored report.
- **Environment variables are debug-only, all prefixed, and only prefixed** (ADR-024): read them through `simple_code_indexer.env.get`, never `os.environ` directly in a settings path, or the `SIMPLE_CI_` spelling rule is lost. There is no bare-name fallback — `env.get("LOG_LEVEL")` reads `SIMPLE_CI_LOG_LEVEL` and nothing else — so a `WORKSPACE_ROOT` left in a shell profile is silently ignored by design. Production paths (harness entries, the spawned sidecar daemon) use flags (`--workspace`, `--harness`, `--index-db`). Third-party names (`COMSPEC`, `ProgramFiles`, `HF_TOKEN`, `XDG_RUNTIME_DIR`, Cline's `CLINE_*`) are never ours to rename.
